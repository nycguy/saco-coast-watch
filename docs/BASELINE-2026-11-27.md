## Current architecture

- GitHub Pages serves a framework-free static SacoCast and EastCast application.
- `Refresh marine winds and deploy dashboard` retrieves NOAA/NWS/NDBC data, builds the fixed-window briefing, captures webcam previews, assembles the site, uploads a Pages artifact, and deploys Pages.
- `Capture coastal history` independently writes durable history and selected Ferry Beach frames to the `coastal-history` branch.
- `Release coastal alerts Worker` is manual and preflight-gated. Cloudflare Worker/D1, Resend, VAPID keys, subscriber rows, and notification preferences are outside the Pages deployment path.
- The browser also retrieves current NOAA/NWS data directly and refreshes its in-memory state. Static snapshots are fallback and briefing/history inputs.

No wholesale rewrite is justified by this baseline. The existing separation of durable history and notification delivery is valuable and is preserved.

## Actions execution baseline

The public Actions API was inspected for runs created from 2026-08-29 through 2026-11-27. In the available sample:

- Pages refresh: 279 runs, 231 successful and 48 failed. Median start-to-start gap was approximately 230 minutes, despite the configured ten-minute schedule.
- Durable history: 212 runs, 211 successful and 1 failed. Median start-to-start gap was approximately 293 minutes, despite the configured fifteen-minute schedule.
- The observed schedule is best-effort and heavily coalesced or delayed by GitHub. It is not a ten-minute or fifteen-minute guarantee.
- Recent successful Pages refreshes generally took roughly 1.5 to 3 minutes. Recent history runs generally took roughly 1 to 2 minutes, with variation by source and archive work.

The sample is based on public workflow metadata and is not a billing-account usage export. Account-wide Actions, Pages, Cloudflare, D1, KV, Resend, and bandwidth consumption could not be independently verified from repository access alone.

## Deployment failure diagnosis: run 45727373906

Evidence from the run log:

1. Site assembly and schema validation passed.
2. `actions/upload-pages-artifact@v5.0.0` uploaded 934,879 bytes and finalized artifact ID `15075416515` successfully.
3. About 300 milliseconds later, `actions/deploy-pages@v5.0.1` queried artifact metadata and received zero artifacts named `github-pages`.
4. The run then failed with `No artifacts named "github-pages" were found for this workflow run`.

The evidence supports a short-lived GitHub Actions artifact registration/propagation race between successful upload finalization and the deploy action's metadata lookup. It does not support a malformed artifact, missing Pages permission, canceled concurrency group, workflow configuration syntax failure, or source-data failure as the cause of this incident.

The workflow now polls the run's artifact metadata endpoint for a bounded period before invoking `deploy-pages`. This is a low-risk mitigation for the observed failure mode. It does not claim that GitHub Pages or Actions scheduling is deterministic.

The first validation run after that change (`45929136298`) failed earlier, during browser setup, because `ubuntu-latest` resolved to Ubuntu 26.04 and Playwright 1.60 explicitly rejected Chromium installation on that image. Data processing and artifact-contract validation passed; Pages publication was correctly skipped by the failed pre-publish browser gate. The Pages, history, and Worker workflows now pin the standard runner to Ubuntu 24.04, which is compatible with the repository's pinned browser toolchain and avoids another moving-image failure.

## Open modernization decisions

The next major phase should independently publish generated data before removing routine scheduled Pages deployments. A dedicated data branch/raw delivery path is possible, but it must first be tested for browser CORS, cache invalidation, rate limits, atomicity, and mobile latency. Until those tests pass, the existing Pages publication path remains the last-known-good delivery mechanism and is not removed.
