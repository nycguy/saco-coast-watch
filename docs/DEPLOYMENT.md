# SacoCast deployment

`nycguy/saco-coast-watch` (`main`) is the only maintained source of truth. GitHub Pages serves `https://nycguy.github.io/saco-coast-watch/`.

## Static site and data

The public `Refresh marine winds and deploy dashboard` workflow refreshes wind/coastal-alert snapshots and publishes Pages every ten minutes, plus its current NOAA/NWS/NHC, EastCast, webcam, fixed-window briefing, and durable-history behavior. The `Capture coastal history` workflow continues to write captured history to the dedicated `coastal-history` branch every 15 minutes. Both workflows run standard public GitHub-hosted Ubuntu runners. The Pages job validates generated data and the assembled artifact on every run. Application pushes and manual refreshes also run all deterministic Python/Node tests, syntax checks, Chromium desktop/mobile browser smoke tests, and live Pages smoke checks. Routine schedules skip those full test suites while retaining data/artifact checks. No private repository is checked out or invoked.

The ten-minute publication cadence halves scheduled Pages refreshes from 288 to 144 per day. The independent history workflow remains at 96 scheduled captures per day to preserve its 15-minute rolling history. Recent scheduled runs averaged about 151 seconds for Pages refresh and 46 seconds for history capture. That implies roughly 13.3 standard-runner hours/day before and 7.3 after, a 45% reduction in scheduled runner time; the runners are standard GitHub-hosted runners on a public repository, with no paid/larger runner or new recurring service. Publication freshness changes from a nominal five-minute to ten-minute schedule; NOAA/NWS direct browser feeds and the 60-second browser refresh remain unchanged. GitHub may delay either schedule.

Run `bash scripts/validate-local.sh` before committing. It runs Python and JavaScript tests/syntax, builds `dist`, verifies the artifact, and runs Chromium desktop/mobile browser checks. Install its browser-only dependencies with `python3 -m pip install playwright pillow && python3 -m playwright install chromium`.

## Cloudflare Worker and D1

The Worker source is `alerts/src/worker.mjs`; migrations are under `alerts/migrations/`. A production release is separate from Pages and only starts through the public `Release coastal alerts Worker` workflow. Its default dispatch is read-only. The read-only preflight confirms current Worker/email health, checks the base email schema, classifies the push schema as wholly absent or complete, captures an aggregate subscriber count, and confirms the existing VAPID secret *names* without reading key values. Partial/unknown schemas, a partial VAPID pair, failed health, or changed subscriber counts stop the release.

Only an explicit dispatch with `apply_migrations_and_deploy=true` can run migrations or deploy. It applies migrations 0002–0004 only when the core additive push schema is absent and applies migration 0005 when custom-threshold device preferences are pending. It verifies all expected tables, columns, and indexes after migration. It never applies 0001 to production. If a complete VAPID pair already exists, the workflow preserves it. If neither VAPID key exists, the workflow may create the first pair only after confirming there are zero existing push devices; a partial pair always stops the release to avoid identity rotation. The post-deploy gate retries briefly for Worker propagation, then verifies email state, D1 schema, push configuration, and the existing health endpoint. It does not send a test notification or synthetic hazard. Cloudflare credentials are GitHub Actions secrets named `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`; values must never be printed or committed.

Deploying the Worker applies its configured ten-minute cron. That runs the existing custom-threshold checker plus the official coastal-event lifecycle path. Custom thresholds can deliver independently by Email, App notification, or both; App-only thresholds require no email address. The event worker establishes a baseline first and does not send a notification for the already-active initial state. Do not lower thresholds or manufacture a hazard to test delivery.

## Production verification

After Pages deployment, verify the live URL and critical static assets/data, desktop and iPhone-sized layouts, EastCast, webcam state, and browser console. Verify Worker `/health` and `/push/config` using the allowed Pages origin. Keep D1 migration state and subscriber-count evidence from the release action. After a push/schema rollout, run the default read-only Worker workflow once more and require `complete` push schema, a complete VAPID pair, `webPushEnabled=true`, and `thresholdPushEnabled=true` before declaring the release complete. A real push delivery test is optional and requires an owner-controlled browser subscription; it sends one test notification only to that device, then disables and removes the test subscription. Never use actual subscribers for synthetic tests.

No paid/larger runners, external paid service/API, or private-source mirror may be introduced without explicit approval. Production secrets, D1 rows, and Worker state must never be copied into repository files or logs.
